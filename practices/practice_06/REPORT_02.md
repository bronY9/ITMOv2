# Отчёт 2. Повторные атаки после исправлений

## Результат повторной проверки

Повторены те же запросы после исправления `service.py`. Безопасность теперь определяется
серверной сессией, проверкой владельца и allowlist действий, а не заголовками клиента или ответом
модели.

| Проверка | Ожидаемое и фактическое поведение после исправления |
|---|---|
| Анонимный доступ к профилям, заказам, файлам, логам и AI | `401 login required` |
| Alice читает профиль/заказ Bob | `403` или `404` без раскрытия существования объекта |
| SQL payload в `search` | Значение передаётся параметром, данные не раскрываются |
| Клиент передаёт `price=1` | Заказ сохраняется по каталожной цене `5000` |
| Alice подделывает `X-Role: staff` | `403`, заголовок не влияет на серверную роль |
| Alice запрашивает чек Bob или служебную заметку | `403 file access denied` |
| Вредоносный отзыв открывается в HTML | Теги экранированы как текст |
| Клиент вызывает `export_profiles` через AI executor | `403 assistant tool access denied` |
| Клиент или LLM вызывает `delete_tree('.')` | `403 destructive tool is disabled`, файлы остаются |
| LLM просит прочитать чек Bob от имени Alice | `403 assistant file access denied` |
| Staff читает debug logs | Доступ разрешён, пароли и токены заменены на `<redacted>` |
| Некорректный JSON | Контролируемый `400`, внутренний тип исключения не раскрывается |

Точный исправленный контекст и ответ executor-а сохранены в `evidence/after/`. Даже если LLM
проигнорирует промпт и вернёт опасный JSON, сервер отклоняет его. Это основное доказательство
защиты от prompt injection и excessive agency.

## Реализованные меры

- обязательная сессия на всех чувствительных маршрутах;
- роли только из серверной сессии, object-level authorization для профилей, заказов и чеков;
- параметризованный SQL и проверка числовых ID;
- цена исключительно из серверного каталога;
- staff-only журналы с редактированием паролей и токенов;
- HTML escaping и ограничения входа для отзывов;
- контекст AI содержит только собственный заказ и явно размеченные недоверенные данные;
- executor разрешает клиенту только точный путь собственного чека;
- destructive tool отключён, экспорт доступен только настоящей staff-сессии;
- контролируемые ответы на malformed JSON и неверный Content-Type.

## Проверки

`make test` в `practice_06` запускает функциональные, HTTP, sandbox и security regression tests.
Фактический результат после исправлений: **30 тестов, все прошли**.

Дополнительно корневой `make step6` вызывает тот же набор. `sandbox.py` не менялся, внешний shell
или сеть не использовались.

## Выводы

Главная проблема исходной архитектуры была не в том, сможет ли конкретная модель распознать
prompt injection, а в том, что сервер доверял её решению. После исправления LLM остаётся
недоверенным планировщиком: окончательные полномочия вычисляются заново на сервере.

Второй вывод — аутентификация без проверки конкретного объекта недостаточна. Токен пользователя
не должен позволять выбрать чужой ID, путь или цену. Поэтому защита построена вокруг серверной
сессии, владельца ресурса, параметризованных запросов и минимального allowlist действий.
