# Рефлексия

До этой работы я воспринимал спецификацию в основном как описание готовой идеи. Здесь оказалось, что самые спорные решения появляются ещё до реализации, когда UI и серверная логика договариваются о поведении на общей границе. Нужно было определить, даёт ли успешный preview разрешение на review, кто отвечает за тексты ошибок, как одинаково считать длину Unicode и что делать с результатом preview после редактирования. В итоге настоящий review всегда проверяет данные заново, контракт опирается на HTTP-статусы, длина считается в code points, а интерфейс сбрасывает устаревший результат и блокирует повторное нажатие во время запроса. Все эти решения можно увидеть, если сравнить черновики из `before/` с итоговыми `ui-spec.md`, `logic-spec.md` и `contracts/shared-contract.md`.

OpenSpec и Spec Kit помогли посмотреть на одну функцию с двух сторон. В OpenSpec единицей работы является change с delta-spec. История изменения хранится в proposal, design и archive, постоянные правила находятся в `openspec/config.yaml`, а документы проверяются через strict validate. Такой процесс оказался удобным для небольшого изменения существующего API: разницу видно сразу, а после archive она попадает в основную спецификацию. При этом в нём меньше места для независимых взглядов нескольких команд.

В Spec Kit работа строится вокруг feature и пользовательских сценариев. Constitution задаёт постоянные правила, затем появляются spec, plan и tasks, а согласованность проверяется через quality checklist, analyze и converge. Документов получилось больше, зато можно проследить путь от пользовательского сценария до общего контракта и конкретной задачи. Для этой домашней работы это было полезно: два исходных черновика сохранились отдельно, а спорные решения были приняты до начала реализации.

После написания кода я проверил не только успешный сценарий. Preview использует те же правила и не вызывает LLM, а настоящий review повторяет валидацию и вызывает модель один раз. Отдельные тесты проверяют 20 001 пробельный символ, безопасный вывод HTML-подобного комментария, сохранение введённого текста после ошибки, сброс preview после редактирования и защиту от двойного запроса. Я также проверил страницу на ширине 320 пикселей, подписи элементов, live-статус и alert. Теперь для небольшого изменения уже знакомого API я бы выбрал OpenSpec, а для работы нескольких команд с отдельными зонами ответственности использовал бы Spec Kit.
