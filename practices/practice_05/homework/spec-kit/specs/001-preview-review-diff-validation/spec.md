# Feature Specification: Preview Review Diff Validation

**Feature Branch**: `practice_05`  
**Created**: 2026-10-22  
**Status**: Accepted  
**Input**: Дать пользователю понятную предварительную проверку diff и сохранить
существующее ревью без лишнего обращения к модели.

## User Scenarios & Testing

### User Story 1 - Проверить diff до ревью (Priority: P1)

Пользователь вставляет diff и заранее узнаёт, принимает ли система эти данные, не
расходуя запуск ревью.

**Why this priority**: Это основная новая ценность и самый короткий законченный сценарий.

**Independent Test**: Ввести допустимый, пустой, пробельный и слишком длинный текст;
получить однозначный результат проверки без запуска ревью.

**Acceptance Scenarios**:

1. **Given** допустимый diff, **When** пользователь запускает проверку, **Then** он
   видит подтверждение допустимости, а ревью не запускается.
2. **Given** пустой или пробельный diff, **When** пользователь запускает проверку,
   **Then** он видит понятную ошибку и сохраняет введённый текст.
3. **Given** diff длиннее 20 000 символов, **When** пользователь запускает проверку,
   **Then** он видит сообщение о превышении лимита.

---

### User Story 2 - Запустить существующее ревью (Priority: P2)

Пользователь отправляет допустимый diff на ревью и видит текст комментария на той же
странице.

**Why this priority**: Сценарий завершает путь пользователя, но базовое ревью уже
существует.

**Independent Test**: Ввести допустимый diff, запустить ревью и получить один текстовый
комментарий; затем убедиться, что недопустимый diff не запускает ревью.

**Acceptance Scenarios**:

1. **Given** допустимый diff, **When** пользователь запускает ревью, **Then** исходный
   текст обрабатывается один раз и комментарий безопасно отображается.
2. **Given** недопустимый diff, **When** пользователь запускает ревью напрямую,
   **Then** система повторно проверяет данные и не запускает обработку.

---

### User Story 3 - Исправить ошибку без потери работы (Priority: P3)

Пользователь меняет diff после ошибки или успешной проверки и продолжает работу без
перезагрузки страницы.

**Why this priority**: Это делает основной сценарий объяснимым и устойчивым.

**Independent Test**: Получить ошибку, изменить поле, проверить устаревание прежнего
статуса и успешно повторить запрос.

**Acceptance Scenarios**:

1. **Given** показана ошибка, **When** пользователь исправляет diff, **Then** текст
   сохраняется, а прежний результат перестаёт считаться актуальным.
2. **Given** запрос уже выполняется, **When** пользователь повторно активирует действие,
   **Then** второй запрос не создаётся.

### Edge Cases

- Ровно 20 000 символов принимаются, 20 001 отклоняется как превышение лимита.
- Слишком длинная пробельная строка отклоняется по длине, а не по содержимому.
- Окружающие пробелы в допустимом diff сохраняются.
- Emoji и другие Unicode-символы считаются как пользовательские символы.
- Недоступная предварительная проверка отличается от ошибки данных.
- Текст комментария с HTML-подобными фрагментами остаётся обычным текстом.

## Requirements

### Functional Requirements

- **FR-001**: Система MUST предоставлять одну страницу для ввода, проверки и ревью diff.
- **FR-002**: Пользователь MUST видеть текущую длину diff относительно лимита 20 000.
- **FR-003**: Система MUST проверять тип, непустое содержимое, значимый символ и длину.
- **FR-004**: Предварительная проверка MUST завершаться без запуска ревью.
- **FR-005**: Превышение лимита MUST иметь приоритет над проверкой пробельного содержимого.
- **FR-006**: Настоящее ревью MUST повторно проверять данные независимо от preview.
- **FR-007**: Допустимый diff MUST передаваться без обрезки и нормализации.
- **FR-008**: Одно пользовательское действие MUST создавать не более одного запроса.
- **FR-009**: Изменение diff MUST делать прежний preview неактуальным.
- **FR-010**: Ошибка MUST сохранять введённый пользователем текст.
- **FR-011**: Комментарий MUST отображаться как текст, а не исполняемая разметка.
- **FR-012**: Существующие успешные ответы ревью и MCP MUST остаться совместимыми.

### Key Entities

- **Review Diff**: исходный текст, его длина и факт наличия непробельного символа.
- **Preview Result**: однозначное подтверждение допустимости без комментария ревью.
- **Review Result**: один текстовый комментарий для допустимого исходного diff.
- **UI State**: редактирование, запрос, успех, ошибка или устаревший preview.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Пользователь получает результат preview одним действием без запуска ревью.
- **SC-002**: Все согласованные границы 20 000/20 001 и виды невалидного ввода дают
  предсказуемый результат в 100% автоматизированных сценариев.
- **SC-003**: Один сквозной браузерный сценарий проходит от открытия страницы до
  preview и отображения комментария.
- **SC-004**: Все прежние автоматизированные проверки API и MCP продолжают проходить.
- **SC-005**: Интерфейс доступен с клавиатуры и сохраняет рабочий сценарий на ширине 320 px.

## Assumptions

- Интерфейс и API доступны с одного источника.
- Пользователь самостоятельно вставляет текст diff.
- Предварительная проверка помогает, но не выдаёт долговременное разрешение на ревью.
- Аутентификация, история, загрузка файлов, редактирование секретов и обработка ошибок
  внешней модели остаются за пределами этой фичи.
